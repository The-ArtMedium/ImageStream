Comment penser avant de taper

Vous savez déjà
comment interroger

Avant d'apprendre la syntaxe SQL, comprenez ceci : vous interrogez des données depuis toute votre vie. Chaque fois que vous avez posé une question sur un groupe de choses, vous faisiez ce que fait une base de données.

Vous pensez
« Montre-moi tous les photographes portrait notés au-dessus de 4.5 »
SELECT name, rating
FROM photographers
WHERE specialty = 'Portrait'
  AND rating > 4.5;
Vous pensez
« Qui sont les 3 meilleurs gagnants cette année, triés par total de tarifs ? »
SELECT photographer_id, SUM(fee_usd)
FROM shoots
GROUP BY photographer_id
ORDER BY SUM(fee_usd) DESC
LIMIT 3;
Vous pensez
« Quelles spécialités ont plus de deux photographes ? »
SELECT specialty, COUNT(*)
FROM photographers
GROUP BY specialty
HAVING COUNT(*) > 2;
Vous pensez
« Donne-moi toutes les séances à Lagos ou Nairobi triées par les plus récentes »
SELECT * FROM shoots
WHERE location IN ('Lagos', 'Nairobi')
ORDER BY year DESC;
Le changement de perspective

SQL ne vous demande pas de penser comme un programmeur. Il vous demande de penser comme quelqu'un qui pose une question claire sur des informations organisées. Si vous pouvez formuler la question en langage simple d'abord, le SQL s'écrit presque tout seul.

Le diagramme le plus important en SQL

L'ordre dans lequel vous l'écrivez
n'est pas l'ordre dans lequel il s'exécute

Ce seul malentendu cause plus de confusion que tout autre en SQL. Vous écrivez une requête dans un ordre. La base de données l'exécute dans un ordre complètement différent. Une fois que vous voyez cela, les messages d'erreur commencent à avoir un sens.

4

5

filtrer les groupes

7

combien de lignes

L'ordre dans lequel la base de données l'exécute

FROM
aller chercher la table en premier
2
WHERE
retirer les lignes qui ne correspondent pas
3
GROUP BY
former les groupes
4
HAVING
retirer les groupes qui ne correspondent pas
5
SELECT
maintenant choisir les colonnes
6
ORDER BY
trier ce qui reste
7
LIMIT

Pourquoi c'est important — trois choses que cela explique immédiatement
  • Pourquoi vous ne pouvez pas utiliser un alias SELECT dans WHERE — SELECT ne s'est pas encore exécuté quand WHERE s'exécute
  • Pourquoi WHERE ne peut pas utiliser COUNT() ou AVG() — ceux-ci sont calculés dans SELECT, qui s'exécute plus tard
  • Pourquoi HAVING existe même — il s'exécute après GROUP BY, donc il peut filtrer en utilisant des résultats agrégés que WHERE ne voit jamais
Une question qui vaut la peine d'être posée

HAVING peut-il exister
sans GROUP BY ?

Oui. Et comprendre pourquoi révèle que vous comprenez vraiment ce que fait GROUP BY — pas seulement où le taper.

Ce qui se passe sans GROUP BY

Quand il n'y a pas de GROUP BY, la table entière est traitée comme un seul groupe. Chaque ligne appartient à ce groupe unique. Donc HAVING s'applique à toute la table comme si c'était un seul groupe.

Cette requête est techniquement valide :

SELECT COUNT(*) AS total
FROM photographers
HAVING COUNT(*) > 5;

Elle demande : la table photographers entière a-t-elle plus de 5 lignes ? Si oui, retourne le compte. Si non, ne retourne rien. Presque jamais ce que vous voulez réellement — mais cela fonctionne, et savoir pourquoi cela fonctionne signifie que vous comprenez la fondation.

Techniquement valide
HAVING sans GROUP BY traite toute la table comme un seul groupe. La requête s'exécutera sans erreur.
Presque jamais utile
Si vous vous retrouvez à écrire HAVING sans GROUP BY, vous voulez presque certainement WHERE à la place — ou vous devez ajouter un GROUP BY.
Le test de fondation

Si quelqu'un vous demande « HAVING peut-il exister sans GROUP BY ? » et que vous pouvez répondre clairement — vous comprenez l'ordre d'exécution. Cela veut dire que WHERE, HAVING, GROUP BY, et les fonctions d'agrégation ne vous embrouilleront plus jamais. C'est la fondation. Tout le reste n'est que syntaxe.

Un analyste de données utilise typiquement SQL pour demander « donne-moi toutes les séances de 2023 avec un tarif supérieur à 500 » — en extrayant les données de la base.
